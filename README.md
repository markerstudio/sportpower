# نظام سبورت باور الداخلي — SportPower Internal System

نظام إدارة داخلي كامل بالعربية (RTL) لشركة **سبورت باور**، مبني وفق البريف الرسمي
وبهوية SportPower البصرية (مشروع SportPower Design System في Claude Design).

## التشغيل محليًا (وضع العرض)

```bash
npm install
npm start          # http://localhost:3000
npm run seed       # إعادة تهيئة البيانات التجريبية
```

بلا إعداد: يخزّن في `data/db.json` مع بيانات تجريبية كاملة (وضع العرض).

## النشر للإنتاج — ربط قاعدة بيانات حقيقية ✅

التخزين الدائم عبر **Postgres مُدار**: عند ضبط `DATABASE_URL` ينتقل النظام
تلقائيًا إلى Postgres بجداول علائقية حقيقية (أعمدة بأنواعها، مفاتيح أجنبية،
فهارس، وترحيلات متتبَّعة)، وخصم الحصص داخل معاملة ذرّية بقفل صف الاشتراك.

### الخطوات على Supabase + Vercel

النظام يعمل مع أي Postgres مُدار (Supabase وNeon وغيرهما) — الموصى به
**Supabase**: تسعيرة ثابتة بلا عدّاد ساعات معالجة، فلا مفاجآت في الفاتورة
مع نظام داخلي يُستخدم طوال اليوم.

1. أنشئ مشروعًا على [supabase.com](https://supabase.com) (الخطة المجانية
   تكفي للبداية — 500 MB وتبقى متاحة مع الاستخدام اليومي).
2. من **Connect** في لوحة المشروع انسخ رابط **Transaction pooler**
   (المضيف يحوي `pooler`، منفذ `6543`). هذا مهم: على Vercel تُنشأ نسخة لكل
   طلب تقريبًا، والاتصال المباشر يستنفد حدّ اتصالات القاعدة تحت الحمل.
   (النظام ينبّهك في السجل إن استُخدم رابط غير مجمَّع على بيئة لحظية.)
   لتشغيل السكربتات محليًا (`db:setup` وغيرها) استخدم رابط
   **Session pooler** (منفذ `5432`).
3. تحقق من الرابط محليًا قبل النشر — يفحص الرابط ويتصل ويطبّق الترحيلات
   ويختبر الكتابة والقراءة، وينبّهك إن كان الرابط مباشرًا بدل المجمَّع:

   ```bash
   DATABASE_URL="postgres://…" npm run db:setup
   ```
4. في **Environment Variables** أضف:
   - `DATABASE_URL` — الرابط المجمَّع. (`POSTGRES_URL` مدعوم أيضًا.)
   - `PGSSL_CA` — **إلزامي مع Supabase**: شهادة الجذر الخاصة بهم (Project
     Settings → Database → SSL → Download certificate) — محتوى ملف `.crt`
     كاملًا. بدونها يفشل الاتصال بخطأ `SELF_SIGNED_CERT_IN_CHAIN` لأن
     النظام يتحقق من هوية الخادم ولا يقبل شهادة غير موثوقة. (Neon يستخدم
     شهادات عامة فلا يحتاجها.)
   - `ADMIN_PASSWORD` — كلمة مرور قوية لحساب `admin`. إن لم تُضبط تُولَّد كلمة
     عشوائية وتُطبع **مرة واحدة** في سجل النشر (Vercel → Logs) — سجّلها من هناك.
     في الحالتين لا يفتح الحساب أي مسار قبل تغييرها من داخل النظام.
5. أعد النشر، ثم تحقق:
   `/api/health` → `{"ok":true,"storage":"postgres","schemaVersion":4,"latencyMs":…}`
   `schemaVersion` يؤكد أن النشر طبّق كل الترحيلات.

عند أول تشغيل على قاعدة فارغة يُزرع الحد الأدنى: حساب المدير + الفروع +
مكتبة الوجبات + الباقات — بلا حسابات تجريبية. لبيئة عرض أضف `SEED_DEMO=1`.

### تأمين واجهة Supabase العامة (Data API)

Supabase يفتح لكل مشروع واجهة REST مولَّدة تلقائيًا على
`https://<المشروع>.supabase.co/rest/v1/` تخدم جداول مخطط `public` لكل
من يحمل مفتاح `anon` — ومفتاح `anon` يُعامل عندهم كقيمة **علنية**.
هذا النظام لا يستخدم تلك الواجهة إطلاقًا (المتصفح يخاطب خادم Express
وحده، والخادم يخاطب القاعدة عبر `DATABASE_URL`)، لذلك يقفلها الترحيل
`#4` تلقائيًا — وهو ما يعالج تنبيه Supabase الأمني
`rls_disabled_in_public`:

- **Row-Level Security** مفعّل على كل جداول `public` بلا سياسات — أي
  منع تام لكل الأدوار عدا مالك الجداول، واتصال الخادم هو المالك فلا
  يتغير سلوك النظام في شيء.
- صلاحيات دوري الواجهة `anon` و`authenticated` مسحوبة عن المخطط كله،
  حاضرًا ومستقبلًا (دفاع إضافي فوق RLS).
- الإجراء يعاد عند كل إقلاع: أي جدول جديد — من تحديث للنظام أو من
  لوحة Supabase — يؤمَّن تلقائيًا، وأي صلاحية أعيدت تُسحب من جديد.
  (على Postgres آخر — محلي أو Neon — لا وجود للدورين فيُتخطى السحب،
  وتفعيل RLS بلا أثر على المالك.)

يبقى إجراء واحد مستحسن بيدك (لا يعتمد عليه الأمان): عطّل الواجهة
كليًّا من **Project Settings → Data API** أو أزل `public` من
**Exposed schemas**. وللتحقق بعد النشر:

- `npm run db:check` يطبع: «الواجهة العامة مقفلة: RLS مفعّل على كل
  الجداول ولا صلاحيات لأدوار anon/authenticated».
- **Security Advisor** في لوحة Supabase يخلو من `rls_disabled_in_public`
  (قد تظهر ملاحظة معلوماتية «RLS enabled, no policy» — هذا هو التصميم
  المقصود يعمل).

إن قررت يومًا استعمال الواجهة العامة فعلًا (supabase-js من المتصفح)
فستحتاج عكس هذا بقصد: إعادة منح الصلاحيات وكتابة سياسات RLS لكل جدول.

### الانتقال بين مزوّدين (Neon → Supabase مثلًا)

`npm run db:migrate` ينقل كل البيانات من قاعدة إلى أخرى مع الحفاظ على
المعرّفات ثم يتحقق جدولًا جدولًا (العدد وأعلى معرّف). المصدر يُقرأ فقط:

```bash
SOURCE_URL="postgres://…(القاعدة الحالية)" \
TARGET_URL="postgres://…(القاعدة الجديدة — رابط Session pooler)" \
npm run db:migrate
```

بعده: `DATABASE_URL="<الهدف>" npm run db:check` للاطمئنان، ثم حدّث
`DATABASE_URL` في Vercel إلى رابط Transaction pooler وأعد النشر، وأبقِ
القاعدة القديمة أسبوعًا كنسخة احتياطية قبل حذفها. الهدف يجب أن يكون
فارغًا (`--force` يمسحه لإعادة المحاولة)، ويُستحسن إيقاف الاستخدام
دقائق أثناء النقل حتى لا تُكتب بيانات جديدة على المصدر بعده.

### الترقية من نسخة سابقة — تلقائية وآمنة

إن كانت قاعدتك تعمل بالتخزين القديم (`id + data JSONB`) فالترقية تجري وحدها
عند أول تشغيل: تُحفظ الجداول القديمة كنسخة احتياطية بلاحقة `_legacy_v1`،
تُنقل الصفوف إلى الأعمدة الجديدة بمعرّفاتها، تُنظَّف المراجع المعلّقة (يُفرَّغ
الاختياري ويُحذف الصف اليتيم إن كان المرجع إلزاميًا) مع تسجيل كل تصحيح في
السجل، ثم تُفعَّل المفاتيح الأجنبية. لا تُحذف النسخة الاحتياطية تلقائيًا —
احذفها يدويًا بعد أن تطمئن.

### التشغيل والصيانة

```bash
npm run db:setup      # ربط القاعدة والتحقق منها خطوة بخطوة (ابدأ من هنا)
npm run db:check      # فحص سلامة البيانات (ثوابت الحسابات والمراجع)
npm run db:backup     # نسخة احتياطية → backups/ (يحتفظ بآخر 14)
npm run db:restore -- backups/sportpower-XXXX.dump
npm run db:migrate    # نقل البيانات بين قاعدتين (SOURCE_URL/TARGET_URL)
npm run load-test     # اختبار حمل على قاعدة اختبار (لا الإنتاج)
```

**تمرين الاستعادة:** نسخة لم تُجرَّب استعادتها ليست نسخة احتياطية. مرة كل شهر:
أنشئ قاعدة فارغة، استعد إليها بـ `RESTORE_URL=… npm run db:restore -- <ملف>`،
ثم شغّل `npm run db:check` عليها. المزوّد يأخذ نسخه تلقائيًا (Supabase
يأخذ نسخًا يومية على الخطط المدفوعة)، لكن نسخة بيدك تعني ألا تعتمد
على مزوّد واحد.

### ملاحظة على حزمة Excel

`xlsx` تُثبَّت من موقع SheetJS الرسمي لا من npm:
`https://cdn.sheetjs.com/xlsx-0.20.3/xlsx-0.20.3.tgz`. النسخة المنشورة على
npm متوقفة عند 0.18.5 وفيها ثغرتان معروفتان (تلويث النموذج الأولي، و ReDoS)
بلا إصدار تصحيحي هناك — والمشروع انتقل إلى موقعه. الرابط مثبَّت ببصمة
`integrity` في `package-lock.json`، فالتثبيت مُعاد ومُوثَّق. يحتاج البناء
وصولًا إلى `cdn.sheetjs.com`.

### تخزين الصور الدائم (Supabase Storage)

صور المتابعة وقراءات InBody تُخزَّن في **دلو Supabase خاص** حين تُضبط
المتغيّرات أدناه؛ وإلا فعلى القرص المحلي (تطوير/عرض). على Vercel، القرص
(/tmp) لحظيّ فتزول الصور مع كل نشر — لذا **الإنتاج يحتاج Supabase**.

الإعداد لمرة واحدة (Vercel → Settings → Environment Variables):

| المتغيّر | القيمة |
|---|---|
| `SUPABASE_URL` | `https://<اسم-المشروع>.supabase.co` (من Supabase → Settings → API) |
| `SUPABASE_SERVICE_ROLE_KEY` | مفتاح `service_role` (سرّي — خادميّ فقط، لا يُكشف للمتصفح) |
| `SUPABASE_STORAGE_BUCKET` | اختياري — اسم الدلو (افتراضي `member-uploads`) |

الدلو يُنشأ **خاصًّا** تلقائيًا عند أول رفع إن لم يوجد؛ ولا تُقدَّم الصور إلا
عبر رابطٍ موقّت موقّع أو جلسةٍ صالحة (كما قبل). أعد النشر بعد ضبط المتغيّرات،
وسيؤكّد سجل الإقلاع: `[uploads] ✓ التخزين الدائم مفعّل عبر Supabase`.

⚠️ الصور المرفوعة **قبل** تفعيل Supabase كانت على /tmp وقد زالت — التفعيل
يحفظ ما يُرفع بعده.

### الأمان المطبق

- **تحقق ثنائي (2FA) إلزامي للإدارة والمحاسب**: رموز تطبيق مصادقة (TOTP وفق
  RFC 6238 بلا اعتماد خارجي) + 10 رموز احتياطية تُعرض مرة واحدة وتُخزن مُجزّأة.
  الإدارة تصفّر تحقق أي موظف من صفحة المستخدمين؛ وللطوارئ فقط اضبط
  `MFA_DISABLE=1` مؤقتًا في متغيرات البيئة ثم أزله بعد استعادة الوصول.
- كلمات المرور: **scrypt** بملح لكل مستخدم (وليس تجزئة بسيطة)، بحساب غير
  متزامن فلا يحجز نداءُ تسجيل الدخول حلقةَ الأحداث. الحد الأدنى 8 محارف على
  كل المسارات. أي بصمة قديمة (sha256) تُرقّى تلقائيًا عند أول دخول ناجح.
- الجلسات: رموز عشوائية 256-bit تُخزن **مجزأة** وتنتهي بعد 12 ساعة (تمديد تلقائي).
- تغيير كلمة المرور يُنهي بقية جلسات المستخدم. زر 🔑 في الشريط العلوي.
- حد لمحاولات الدخول: 8 لكل مستخدم / 30 لكل IP كل 15 دقيقة — محفوظ في
  القاعدة لا في ذاكرة العملية، فيصحّ الحدّ مهما تعددت النسخ اللحظية.
- **كلمة المرور المؤقتة لا تفتح النظام**: الخادم يرفض كل مسار عدا `‎/api/me`
  و`‎/api/me/password` و`‎/api/logout` حتى تُغيَّر (وليس تنبيهًا في الواجهة فقط).
- **المرفقات محمية**: صور المتابعة وقراءات InBody لا تُقدَّم بمسار عام —
  الخادم يوقّع رابطًا موقّتًا (HMAC، 6 ساعات) لكل صورة، أو يقبل جلسة صالحة.
- ترويسات أمان: CSP، `X-Frame-Options: DENY`، `nosniff`، `HSTS`، وHTTPS مفروض
  من Vercel. ردود `‎/api` تحمل `Cache-Control: no-store` فلا تبقى بيانات
  شخصية أو صحية في ذاكرة المتصفح أو الوسطاء.
- الصلاحيات مفروضة في الخادم لكل مسار (وليس في الواجهة فقط)، ويشمل ذلك
  تقييد الفرع على الملفات الصحية (InBody، صور المتابعة، خطط التغذية) —
  وهي بلا عمود فرع فتُقيَّد عبر فرع صاحب الملف.
- اتصال القاعدة **يتحقق من شهادة الخادم** (لا تشفير بلا توثيق هوية) —
  يمكن تعطيله للتشخيص فقط عبر `PGSSL_NO_VERIFY=1` مع تحذير في السجل.
- **تصدير CSV آمن**: أي خلية تبدأ بـ `=` أو `+` أو `-` أو `@` تُسبق بفاصلة
  عليا. الاسم يصل من نموذج العقد العام، وبدون ذلك كانت صيغة في خانة الاسم
  تُنفَّذ على جهاز من يفتح الملف بإكسل وتُسرّب الورقة كاملة.
- **زمن تسجيل الدخول ثابت**: الاسم غير الموجود يصرف عمل scrypt نفسه، فلا
  يُكشف أي اسم مستخدم حقيقي من فرق التوقيت.
- **حجم الجسم بحسب المسار**: ١٢٨ كيلوبايت افتراضًا، و١٥ ميغا لمسارات الصور
  والملفات وحدها — فلا يُحلَّل جسم ضخم على مسار بلا مصادقة.
- **المرفقات تُفحص بمحتواها** (بصمة الملف) لا بترويستها، بسقف ٤ ميغا للصورة.
- **سقف زمني للاستعلامات** يمنع استعلامًا شاردًا من احتجاز اتصال.
- **مفاتيح أجنبية** تمنع البيانات اليتيمة على مستوى القاعدة نفسها.
- الأسعار وتقييمات المتدربين محجوبة عن المدرب **في الخادم**، لا في الواجهة.
- الإشعارات **المقروءة** تُنظَّف تلقائيًا بعد مدة الاحتفاظ (غير المقروء يبقى دائمًا).

## أنواع المستخدمين والصلاحيات

- **الإدارة** — تبدأ من **مركز القرارات** (ما الذي يجب فعله اليوم)، وترى كل الفروع والمدربين والمتدربين. داش بورد شامل: حصص يومي/شهري،
  عدد الأشخاص وساعات التدريب لكل مدرب، المتدربون الفعالون، الاشتراكات المنتهية
  والقريبة من الانتهاء، الدفعات والتحصيلات، قراءات InBody. تعدّل البرامج والمواعيد والحصص.
- **المدرب** — حساب خاص، **لا يرى أسعار الاشتراكات ولا الباقات ولا تقييمات المتدربين**
  (إلا بصلاحيةٍ تُمنح له بالاسم — انظر «صلاحيتان تُمنحان لمدرب بعينه» أدناه)،
  جدول حصصه اليومي على Calendar، تنبيه قبل الحصة، والمدربون يتناوبون على المتدربين (الحصة تُنسب لمن نفّذها)،
  تعديل المواعيد، وتسجيل الحصة (المتدرب/التاريخ/الساعة/المدة/الأسلوب/الملاحظات/الوزن).
- **المحاسب** — إدخال المشترك الجديد (Onboarding) والتجديد والتجميد/الإلغاء بسبب مسجَّل،
  البيانات المالية: قيمة الاشتراك/المدفوع/المتبقي/تاريخ وطريقة الدفع، المجددة والمنتهية،
  إضافة وتعديل الدفعات، تسجيل **المصاريف الشهرية** ورؤية **صافي الربح**، متابعة المبيعات (Leads)،
  بروفايل كل متدرب (بياناته واشتراكاته ومدفوعاته)، والأهداف الشهرية/السنوية بوضوح مع الترحيل.
- **المتدرب** — **باقته الحالية والباقات المتاحة**، **تقييم كل حصة أخذها مع تعليق يصل للإدارة**،
  رصيد الحصص (الكلي/المستخدم/المتبقي)، جدول مواعيده، قراءات الوزن
  والـ InBody مع مقارنة، ملاحظات المدرب، تاريخ الاشتراك والانتهاء، برنامجه الغذائي والتدريبي،
  وقسم **«نقاطي ومكافآتي»**: نقاط الولاء وسجلها والمكافآت وكود «ادعُ صديقًا».

### صلاحيتان تُمنحان لمدرب بعينه

الأسعار سرّ تجاري والتجديد قرارٌ ماليّ، فالأصل أن المدرب لا يرى الأولى ولا يملك
الثاني. لكن بعض المدربين يتولّون الاستقبال فعلًا — فتُمنح لهم الصلاحية **بالاسم**
من جدول المستخدمين (الإعدادات والتحكم)، لا لكل المدربين:

| الصلاحية | ماذا تفتح |
|---|---|
| **يرى الأسعار** | الباقات بأسعارها، وصفحة «الباقات والعقود» (اطّلاعًا: لا يفتح عقدًا ولا يعدّله). |
| **يجدّد الاشتراكات** | تجديدُ اشتراك **لمشترك سابق في فرعه هو**. وتشمل رؤية الأسعار تلقائيًا — لا تجديد بلا سعر. |

ما يبقى للإدارة والمحاسبة في كل الأحوال: فتحُ زبون جديد (Onboarding)، التجميد
والإلغاء، تعديلُ الاشتراكات وحذفها، وتسجيلُ الدفعات.

حدودٌ مفروضة في الخادم لا في الشاشة: المدرب المخوَّل لا يُجدِّد لمشترك في فرع آخر،
ولا يفتح اشتراكًا لمن لا اشتراك سابق له، ولا يُجدِّد إطلاقًا إن كان حسابه بلا فرع
مُسنَد. ومنحُ الصلاحية أو سحبها يُنهي جلساته فورًا فلا ينتظر انتهاء الجلسة.

## نظام الحصص (منطق الاحتساب)

عند حفظ حصة من المدرب:
1. تُحفظ الحصة باسم المتدرب وتُخصم حصة من رصيده ويظهر له «متبقي 11 من أصل 12».
2. تُضاف لأداء المدرب الشهري (عدد الحصص + عدد الأشخاص).
3. تُسجل الساعة التدريبية: **أربعة متدربين بنفس الساعة = ساعة تدريب واحدة، وعدد الأشخاص = 4**
   (الساعات تُحسب بالساعات المميزة: مدرب + تاريخ + ساعة بدء — فلا يُحتسب للمدرب
   أكثر من ساعة إن درّب مجموعة في الوقت نفسه).
4. الأرقام تتحدث تلقائيًا في كل اللوحات.

### أنواع الحصة الثلاثة

| النوع | الخصم من الرصيد | الاحتساب في الحضور | الاحتساب للمدرب |
|---|---|---|---|
| **عادية** | ✅ تُخصم | حضور | حصة منفَّذة + ساعة تدريب |
| **غياب** | ✅ تُخصم | **غياب** | لا شيء |
| **تعويضية عن غياب** | ❌ لا تُخصم (خُصمت يوم الغياب) | حضور | حصة منفَّذة + ساعة تدريب |
| **تعويضية بلا غياب معلّق** | ✅ تُخصم | حضور | حصة منفَّذة + ساعة تدريب |

**التعويضية تحلّ محلّ الغياب ولا تُضاف إليه**: عند تسجيلها يبحث النظام عن أقدم غياب
مخصوم لم يُعوَّض بعد ويربطها به بلا خصم جديد — فلا يدفع المتدرب حصتين عن موعد واحد.
وتُسجَّل حتى لو انتهى اشتراكه، لأن حصتها مدفوعة ومستحقة له. أما التعويضية التي تُسجَّل
بلا غياب معلّق فهي حصة نُفّذت فعلًا وتُخصم كالعادية. ورقم «غياب مخصوم بانتظار تعويض»
في ملف المشترك يعدّ ما لم يُعوَّض وحده. وحذف الحصة يُعيدها للرصيد إن كانت قد خُصمت،
وحذف التعويضية يُعيد غيابها «بانتظار التعويض».

**الغياب** هو النوع الذي يحلّ الالتباس القديم: المتدرب لم يحضر، فتُخصم منه الحصة
(هذه سياسة النادي) لكنها **تُسجَّل غيابًا** لا حضورًا — فتظهر في نسبة حضوره، وفي
غيابات الفرع، وفي مركز القرارات كاستحقاق تعويض، ولا تُحسب حصةً منفَّذة للمدرب.
والموعد المرتبط بها يُعلَّم غيابًا تلقائيًا فلا يُحتسب الغياب الواحد مرتين.

المدرب يعدّل حصصه (بما فيها تاريخها وتحويلها بين «عادية» و«غياب») ويحذفها —
والحذف يعيد الحصة إلى رصيد الاشتراك ويعيد الموعد المرتبط إلى «مجدول».

## مركز القرارات (Action Center) — «ماذا يجب أن نفعل الآن؟»

الصفحة الأولى للإدارة والمحاسب: لا تعرض أرقامًا فقط، بل **يحوّل النظام كل مشكلة
يكتشفها في البيانات إلى إجراء جاهز للتنفيذ**. لكل بطاقة: سبب ظهورها، أولويتها،
الشخص أو الفرع المسؤول، وأزرار تنفيذ مباشرة (اتصال · واتساب · فتح ملف المتدرب ·
فتح ملف التجديد · فتح ملف المدرب · إنشاء مهمة).

| الأولوية | القاعدة | الإجراء المقترح |
|---|---|---|
| 🔴 عاجل | متدرب غاب أكثر من مرة خلال 30 يومًا | مهمة تواصل + إعادة جدولة |
| 🔴 عاجل | اشتراك بقي له حصتان أو أقل / ينتهي خلال أسبوع / منتهٍ | مهمة تجديد مع عرض الباقة |
| 🔴 عاجل | متدرب غاب ولم يتم التواصل معه بعده | إشعار لقسم المتابعة |
| 🔴 عاجل | تقييم منخفض (≤2) من متدرب لحصته | مراجعة مع المدرب وإغلاق الشكوى |
| 🟡 مهم | مدرب لم يسجل قياسات لمتدربيه خلال أسبوعين | مهمة مراجعة للمدرب |
| 🟡 مهم | متدرب بلا تقدّم خلال 4 أسابيع (حسب هدفه) | مراجعة الخطة التدريبية والغذائية |
| 🟡 مهم | انخفاض نسبة التجديد في فرع عن الهدف | تنبيه للإدارة مع مراجعة الأسباب |
| 🟢 تحسين | ارتفاع نسبة الغياب في فرع | تفعيل التذكير ومراجعة المواعيد |
| 🟢 تحسين | التحصيل متأخر عن الهدف اليومي (الهدف الشهري ÷ أيام الشهر) | متابعة الدفعات والتجديدات |
| 🟢 تحسين | انخفاض معدل حضور المتدربين النشطين | حملة تنشيط وحجز مواعيد |
| 🟢 تحسين | ملاحظة مكتوبة من متدرب على حصته | الاستفادة منها في تحسين التجربة |
| 🔴 عاجل | **نقص حصص الأسبوع**: الباقة تقتضي ٣ حصص أسبوعيًا وجاء أقل | جدولة الحصص التعويضية المستحقة |
| 🟡 مهم | **إيقاع أسرع من الباقة**: أخذ ٤ حصص في أسبوع | متابعة الإيقاع وتجهيز التجديد مبكرًا |
| 🔴 عاجل | **نفدت الحصص ومدة الاشتراك سارية** | التجديد على الحصص لا على التاريخ |
| 🟡 مهم | **لم يتوزّن هذا الأسبوع** رغم حضوره حصصًا | وزنه في أول حصة وتسجيل القراءة |
| 🔴 عاجل | **مستحق مالي بلا دفعة خلال الأسبوع** | متابعة الدفعة وتسجيلها فور استلامها |
| 🟡 مهم | **مدرب لم يُدخل ساعاته أو مهامه اليومية** | تذكيره أو إدخالها عنه من المتابعة اليومية |
| 🔴 عاجل | **يوم بلا أي إدخال** (كل الأرقام صفر) | التحقق: عطلة أم تقصير في الإدخال؟ |

قاعدة الحصص الأسبوعية تقرأ نصيب الأسبوع من الباقة (`sessionsPerWeek`)، وإن لم يكن
محدّدًا اشتقّته من المدة: ١٢ حصة على ٣٠ يومًا = ٣ حصص أسبوعيًا. وإجراءا **التعويض
والميزان يصلان المتدرب أيضًا** كإشعار في حسابه، مرة واحدة لكل أسبوع.

- **تنفيذ وتتبّع**: «تم التنفيذ» مع تسجيل النتيجة، «تأجيل» لمدة تختارها، وإعادة الفتح —
  وكل ذلك في **سجل الإجراءات** (من نفّذ، ومتى، وبأي ملاحظة).
- **تحويل الإجراء إلى مهمة**: بضغطة تصبح مهمة رسمية على مدرب، تصله بإشعار وتدخل في KPI الشهري.
- **العتبات قابلة للضبط** من المدير (عدد الغيابات، الحصص المتبقية، أيام القياسات، نسب
  التجديد والغياب والحضور…) ويُعاد الفحص فورًا وفقها.
- ملخّص المركز يظهر أعلى لوحة الإدارة قبل الأرقام، ويمكن فلترة الإجراءات حسب الفرع والأولوية.

## الباقات والعقد الإلكتروني

- **الباقات**: كتالوج اشتراكات (اسم، عدد حصص، سعر، مدة، حصص أسبوعية، ما تشمله الباقة)،
  تظهر على **ملف كل مشترك** للتجديد أو الترقية، وتملأ نموذج التسجيل تلقائيًا.
- **نوع التدريب في العقد**: لكل باقة نوع — **تدريب شخصي / تدريب مجموعات / باقات التوفير**.
  الزبون يختار النوع أولًا في العقد فتظهر باقاته، ثم تظهر الباقة المختارة بنوعها في ملخص العقد.
- **العقد الإلكتروني**: الإدارة تفتح رابط عقد وترسله للزبون على واتساب — يفتحه **بلا حساب**،
  يرى **كل الباقات بأسعارها** وسعر الحصة وشروط الاشتراك، يختار باقته ويعبّي بياناته
  (بما فيها الملاحظات الصحية ورقم الطوارئ) ويوافق على الشروط. تصل بياناته للإدارة
  وتحوّله لمشترك بضغطة واحدة (Onboarding معبّأ مسبقًا بباقته وبياناته).
- **سرّية الأسعار**: المدرب وأخصائية التغذية **لا يريان أي سعر** — لا في ملف المشترك،
  ولا في الاشتراكات، ولا في الباقات (مفروض في الخادم وليس في الواجهة فقط).

## الموقع العام والدورات — www.sport-power.net

الموقع العام مشروع منفصل في مجلد `site/` (صفحات ثابتة عربية/إنجليزية
تُبنى بسكربت، وصفحة الدورة تُولَّد عند الطلب) ويُنشر كمشروع Vercel ثانٍ
من المستودع نفسه على النطاق الرئيسي، بينما يبقى النظام على
`app.sport-power.net`. خطوات النشر ونقل النطاق من Wix في `site/README.md`.

ما يربط الاثنين ثلاثة مسارات عامة بلا مصادقة، محدودة المعدّل، وCORS
مقصور على أصل الموقع (`SITE_ORIGINS`):

| المسار | ماذا يعيد / يفعل |
|---|---|
| `GET /api/public/site` | الفروع، الباقات الفعّالة بعملة فرعها، الدورات المنشورة، بيانات التواصل، قائمة الأهداف — بلا أي بيانات شخصية، ويجوز تخزينه على الحافة دقائق |
| `GET /api/public/site/courses/:slug` | دورة واحدة منشورة (لصفحة الدورة) |
| `POST /api/public/site/leads` | طلب انضمام أو اهتمام بدورة → سجل في **متابعة المبيعات** بقناة «الموقع الإلكتروني» + إشعار للإدارة والمحاسبة. حقل فخّ للروبوتات، 6 طلبات لكل IP كل ربع ساعة، والرقم المكرر خلال أسبوع يُلحق بالسجل القائم لا سجلًا جديدًا |

**الحساب لا يُنشأ من الموقع.** الطلب يصل الاستقبال، فيتواصل ويُصدر رابط
العقد الإلكتروني من السجل، ويحوّله لمشترك كما هو نظام العمل — فيبقى
إنشاء الحسابات بيد الموظفين وتحت التحقق الثنائي.

**الدورات** (`courses`): كتالوج ما تسوّقه سبورت باور للمدربين وأصحاب
الأكاديميات، يُدار من صفحة «الدورات والموقع» (الإدارة تحرّر، المحاسبة
تقرأ): عنوان ونبذة ومحاور وباقات (Silver · Gold · Premium) بالعربية
والإنجليزية، ولا تظهر على الموقع إلا المنشورة. تُزرع دورة «من مدرب إلى
بزنس متكامل» مرة واحدة على قاعدة بلا دورات.

**بيانات التواصل** المعروضة على الموقع (هاتف، واتساب، بريد، حسابات
التواصل، العنوان) من الإعدادات → «الموقع الإلكتروني — بيانات التواصل».

## نتائج المشتركين ومشاكلهم — رصد داخلي سرّي

من **صفحة المشترك** ومن **صفحة القراءات** يُرصد على أي متدرب:

- **نتيجة** وصل إليها (نزل ٤ كغ، زاد عضله، حقق هدفه…).
- **مشكلة** ظهرت عنده (إصابة، انقطاع متكرر، عدم التزام بالبرنامج) بدرجة خطورة،
  وتُغلق عند معالجتها.

الرصد **سرّي عن المتدرب تمامًا**: الخادم لا يُرسل هذه السجلات لحسابه إطلاقًا (لا في
ملفه ولا في إشعاراته)، وكل مسارات الرصد ممنوعة على دور المتدرب. تظهر للإدارة
والمحاسب والمدرب وأخصائية التغذية فقط.

وتُجمَّع الحصيلة في ثلاثة أماكن:
- أعلى **صفحة القراءات**: عدد النتائج في كل فرع، وعدد **الأشخاص** الذين عندهم مشاكل.
- **KPI المدرب والفرع**: نتائج ومشاكل متدربيه/الفرع خلال الشهر.
- **التقرير الشهري**: قسم مستقل بالنتائج والمشاكل، ويُصدَّر مع ملف الـ CSV.

## الديون

كل اشتراك بقي عليه مبلغ — **فعّالًا كان أو منتهيًا** — يظهر في «الديون المستحقة» على
اللوحة المالية: المبلغ المتبقي، عمر الدين، وزر تسجيل السداد يفتح النافذة والمبلغ معبّأ
بالمتبقي، وزر واتساب للتذكير. (سابقًا كان خيار «سداد دين» يعرض الاشتراكات المنتهية
فقط، فمن عليه متأخرات على اشتراك فعّال لم يكن له مكان يُسدَّد فيه.)

**دَينٌ سابق للنظام (بلا اشتراك يقابله).** النظام جديد، وعلى بعض المشتركين متأخرات
نشأت قبل تشغيله فلا اشتراك في القاعدة تُعلَّق عليه — وكانت الديون كلها مشتقّة من
الاشتراكات، فلا مكان لها أصلًا. تُسجَّل الآن على الشخص مباشرةً بقيمتها وسببها وتاريخها
(من زر «+ دَين سابق للنظام» في اللوحة المالية، أو من ملف المشترك)، وتظهر مع ديون
الاشتراكات في القائمة والمجاميع نفسها، وتُسدَّد بدفعات كبقية الديون. وسدادُها تحصيلٌ
حقيقي يدخل التقارير و KPI ويُميَّز في سجل الدفعات وتصدير Excel.

**ولصاحب الدَّين حالتان — يُختاران من القائمة نفسها:**

| الحالة | ما يحدث |
|---|---|
| **مشترك مسجَّل عندنا** | الدَّين يُربط بحسابه ويظهر في ملفه، وفرعُه يُقرأ من حسابه. |
| **شخص ليس في النظام** | يكفي اسمه (وجواله اختيارًا) وفرعُه. لا يُفتح له حساب. |

الحالة الثانية لأن تسجيل الجميع ثمنٌ باهظ لقبض دَينٍ قديم: من يدفع متأخراته ثم
ينصرف لا حاجة لفتح حساب باسمه — والمال يدخل التحصيل وسجلَّ الدفعات ومطابقةَ
الصندوق كأي مبلغ آخر، ويظهر في القوائم موسومًا **«غير مسجَّل»**.

ومعه **دفعةٌ في الخطوة نفسها** (اختيارية): تسجيلُ واحدٍ يدفع دَينه فعلٌ واحد عند
المحاسبة لا فعلان — تُملأ خانة «المبلغ المدفوع الآن» فيُسجَّل الدَّين ودفعتُه معًا.

قيود تحفظ الحساب: لا يُخفَّض أصل الدَّين تحت ما سُدِّد منه، ولا يُحذف دَينٌ عليه
دفعات، ولا تتجاوز الدفعةُ قيمةَ الدَّين. وللمشترك المسجَّل يُقرأ الفرع من حسابه لا
من الطلب؛ ولغير المسجَّل — حيث لا حساب يُقرأ منه — يأتي الفرع من الطلب **ويُتحقَّق
منه**، فلا يُسجَّل محاسبٌ مقيَّد دَينًا على فرعٍ خارج نطاقه.

## ولاء المشتركين — نقطة الولاء

يحصل المشترك على **نقطة ولاء** تلقائيًا عند اجتماع ثلاثة شروط معًا:

1. جدّد اشتراكه **في وقته المحدد** (قبل انتهاء الاشتراك السابق أو فيه).
2. دفع كامل القيمة **دفعة واحدة**.
3. كان قد **أنهى كل حصص** اشتراكه السابق.

تُقيَّم الشروط لحظة اكتمال السداد، ولا تتكرر للاشتراك نفسه. وقيمة النقطة تضبطها
الإدارة من صفحة الولاء.

## KPI والأهداف — كل ما يُقاس في مكان واحد

صفحة «الأهداف وKPI» تعرض، مع فلتر الشهر والفرع (وكلاهما محفوظ في عنوان الصفحة،
فالتحديث لا يعيدك للبداية):

- **KPI المدرب**: الساعات المكتبية · ساعات التدريب · عدد الحصص · الغيابات · كم شخصًا
  درّب · التحصيل الناتج عن زبائنه · الستوريات · الريلز · الزبائن الجدد · التجميد ·
  التجديد · النتائج · المشاكل · أهداف متدربيه · برامج الأكل · البرامج التدريبية · المهام.
- **KPI الفروع**: المشتركون الجدد · التجديد · العائدون من التجميد · تجميد الشهر ·
  المجمّدون الآن مقابل **سقف التجميد المسموح للفرع** (يظهر التجاوز بالأحمر) ·
  التحصيل · الفعّالون · نسبة التجديد · النتائج والمشاكل.
- **KPI المحاسب**: التحصيل والمشتركون الجدد والعائدون من التجميد والتجميد — لكل فرع.
- **KPI المبيعات**: الأرقام الجديدة · نسبة الإغلاق · العملاء الجدد هذا الشهر ·
  العائدون من التجميد · عدد الـ test (المحجوزة والحاضرة) وقنوات الوصول.

- **أهداف الموظفين**: كل هدفٍ شخصي بنسبة إنجازه — المحاسبة والمبيعات والتغذية
  والإدارة — في اللوحة نفسها لا في شاشة أخرى.

وتحته **«كيف وصلنا المشتركون الجدد»**: يُختار عند التسجيل — سوشال ميديا (مع المنصة)،
أو عن طريق متدرب عندنا (باسمه)، أو عن طريق صديق (يُختار من المسجّلين أو يُكتب اسمه
إن كان خارج النظام)، أو زبون جديد مباشر، أو عائد من التجميد، أو عن طريق مدرب.
**ويُصحَّح لاحقًا من ملف المشترك** إن أُدخل خطأً، ومعه تاريخ الانضمام الذي يجعله
«مشتركًا جديدًا» في KPI ذلك الشهر.

### الهدف (Target): لمن يُضبط وبأي مؤشر

الهدف لم يعد للشركة والفرع والمدرب فقط. النطاق الرابع **«موظف»** يضبط هدفًا لأي
حساب — محاسبة أو تغذية أو إدارة أو مدرب — فيُقاس **«كل حدا بنحسبه»**.

وكل مؤشر يعلن كيف يُنسب لصاحبه حين يكون النطاق شخصًا:

- **يُقاس على فروعه** — التحصيل، الاشتراكات، التجميد، الفعّالون. فالمحاسبة تُحاسَب
  بأرقام فرعها لا بما سجّلته بيدها («المحاسب: نختار حسب الفرع»).
- **يُقاس على عمله هو** — الحصص والساعات والستوريات والريلز والنتائج وأهداف
  المشتركين وبرامج الأكل، وأرقامُ المبيعات كلها (تُنسب لمن سجّل العميل المحتمل).

المؤشرات المتاحة: التحصيل · عدد الحصص · متدربون فريدون · ساعات التدريب · ساعات
مكتبية · ستوريات · ريلز · **اشتراكات جديدة فقط** · **تجديد اشتراكات** · اشتراكات
جديدة + تجديد (المجموع) · المتدربون الفعالون · مشتركون جدد (أشخاص) · عدد التجميد ·
عائد من التجميد · نتائج · مشاكل · زبائن عن طريقه · أهداف تدريبية وُضعت · برامج أكل ·
أرقام جديدة (مبيعات) · حصص تجريبية (test) · عملاء أُغلقوا · نسبة الإغلاق %.

> **التجديد ليس اشتراكًا جديدًا** — بطلب العميل صراحةً، صارا مؤشرين منفصلين. ومؤشر
> «اشتراكات جديدة + تجديد» يبقى بمعناه القديم فلا ينقلب هدفٌ ضُبط قبل الفصل.

والمؤشر يُرفض على نطاقٍ لا يُقاس عليه (لا «نسبة إغلاق» لمدرب، ولا «ساعات تدريب»
لمحاسبة)، وصاحبُ الهدف يجب أن يكون موجودًا فعلًا — فلا يظهر هدفٌ بنسبة صفر أبدًا
لأن مرجعه محذوف. وجدولُ «KPI الموظفين» صار يعرض كل من له مهامٌ أو هدفٌ هذا الشهر
بدوره ونسبته، لا المدربين وحدهم.

## تقييم الحصص — خاص بالإدارة

المتدرب يقيّم كل حصة أخذها (من 1 إلى 5 نجوم) ويكتب تعليقه بحرّية. التقييم والتعليق
**يصلان للإدارة فقط ولا يراهما المدرب إطلاقًا** (مفروض في الخادم). صفحة «تقييمات المتدربين»
تعرض المتوسط العام، متوسط كل مدرب (الأدنى أولًا)، وكل التعليقات — وأي تقييم منخفض
يتحول تلقائيًا إلى إجراء عاجل في مركز القرارات.

## الميزات

- **Calendar مشترك** أسبوعي: الإدارة تضيف مواعيد وترى جدول كل المدربين معًا مع فلتر،
  المدرب يرى مواعيده ويعدلها، وتصل إشعارات عند الإضافة أو التعديل.
- **InBody Reader**: رفع صورة القراءة و**قراءة كل قيم الورقة تلقائيًا** لا الوزن وحده —
  الوزن، نسبة الدهون، كتلة العضلات، دهون الجسم، الماء، BMI، النقاط، وقياسات شريط
  القياس (الخصر/الصدر/اليد/الحوض/الرجل) — إضافةً إلى **تاريخ الورقة** إن كان مطبوعًا.
  كل قيمة تُقرأ تُميَّز في النموذج ليراجعها المستخدم، وأي قيمة خارج المدى المعقول
  تُترك فارغة (قراءة شاردة أسوأ من خانة فارغة). والإدخال اليدوي متاح دائمًا.
  حفظ كل القراءات حسب التاريخ، ومقارنة أول قراءة بآخرها.
- **الإشعارات**: مواعيد جديدة أو معدلة، تنبيه قبل الحصة، اشتراكات قريبة من الانتهاء، خصم الحصص.
- **التقارير الشهرية** لكل مدرب وفرع + تصدير **Excel (CSV)** و**PDF (طباعة)** — وتشمل
  **تقرير النمو** وفق مؤشرات الشركة: المشتركون الجدد، المجددون ونسبة التجديد (Retention)،
  الإلغاءات ونسبتها وأسبابها، المجمدون ونسبتهم، النمو الصافي (Net Growth)، النشطون،
  متوسط بقاء العميل، قيمة العميل (LTV)، والمقارنة بالهدف الشهري والسنوي.
- **المصاريف الشهرية وصافي الربح**: المحاسب يسجل مصاريف كل شهر (رواتب/إيجار/تسويق…)
  وتظهر في التقرير الشهري مع التحصيل وصافي الربح.
- **الأهداف مع الترحيل التلقائي**: الهدف الشهري لكل فرع ظاهر بوضوح، الهدف السنوي مقسم
  على أشهر السنة، وما لم يتحقق من هدف شهر منقضٍ يُرحَّل تلقائيًا لهدف الشهر التالي.
- **متابعة المبيعات (Leads)**: ملف بكل رقم تم التواصل معه (القناة، السكن، الهدف، المرحلة،
  الاعتراض)، وتحليل شهري: نسبة الإغلاق، أين مشاكل المبيعات (غالي/بعيد/لم يحضر التجربة…)،
  وتحويل العميل المحتمل لمشترك بضغطة واحدة.
- **نظام الولاء «نقاطي ومكافآتي»**: نقاط عند حضور الحصص وتجديد الاشتراك وتحقيق الأهداف
  (منح يدوي من الإدارة)، مكافآت قابلة للاستبدال (خصم/بلوزة/حصة إضافية/شهر مجاني)
  باعتماد الإدارة، وتحكم كامل بقيم النقاط والمكافآت.
- **الإحالات «ادعُ صديقًا»**: كود خاص لكل مشترك ومشاركة عبر واتساب (للاشتراك أو لحصة
  تجريبية)، اعتماد الإحالة من الإدارة يمنح المُحيل نقاطه، مع تقارير بالإحالات والاستبدالات.
- **الحصص التعويضية**: خيار «تعويض» في الجدول اليومي وتسجيل الحصص — تُخصم من رصيد
  الاشتراك كالحصة العادية وتبقى موسومة «تعويض» في السجل والتقارير.
- **حصة Test لزائر جديد**: موعد تجريبي باسم شخص غير مسجَّل (إدخال يدوي بالاسم والجوال،
  بلا حساب ولا اشتراك) — ومنه زر واحد لتسجيله زبونًا كاملًا يُنسب موعده القديم لحسابه.
- **مكان السكن**: حقل لكل مشترك، ومنه تحليل «من أي المناطق يأتي مشتركونا؟» في تقرير
  المتدربين بالأسماء (عدد المتدربين والفعّالين لكل منطقة وتوزّعها على الفروع).
- **تقرير المتدربين بالأسماء**: كل المشتركين بالفرع مع باقتهم وحصصهم ودفعاتهم والمتبقي
  عليهم، وأعمدة اختيارية (الجوال، تاريخ الميلاد، مكان السكن، اسم المستخدم، تاريخ الانضمام،
  آخر حصة) تُختار قبل العرض والتصدير إلى Excel. **وشهرًا بشهر**: اختر شهرًا فيُصفّى سجل
  الدفعات به ويظهر عمود «كم دفع في هذا الشهر»، مع وضع «آخر دفعة لكل شخص فقط». والسجل
  معروضٌ على الشاشة أيضًا لا في الملف وحده، قابلًا للبحث بالاسم أو الفرع أو التاريخ.
- **تنبيه عيد الميلاد قبل يوم**: يظهر في المتابعة اليومية وفي مركز القرارات ويصل إشعارًا
  للإدارة والمحاسب، مع رسالة تهنئة واتساب جاهزة.
- **إرسال بيانات الدخول واتساب**: زر في ملف المشترك وفي جدول المستخدمين يولّد كلمة مرور
  مؤقتة جديدة (تسقط القديمة) ويفتح واتساب برسالة جاهزة فيها الرابط واسم المستخدم وكلمة المرور.
- **البرامج التدريبية**: المدرب ينشئ برنامجًا فيُربط تلقائيًا بكل المتدربين ويصلهم إشعار.
- **مكتبة التغذية**: وجبات بالسعرات والماكروز والمكونات وطريقة التحضير والنوع والهدف،
  إضافة من المدرب/الأخصائية، عرض حسب هدف المتدرب، بحث وفلترة (سعرات/بروتين/نوع/هدف)،
  وربط الوجبات ببرنامج المتدرب اليومي.
- **تصحيح قراءة InBody بعد حفظها**: رقمٌ دخل خطأً — يدويًا أو من OCR — كان يبقى إلى
  الأبد ويجرّ معه الرسم البياني والمقارنة وحكم «هل تقدّم؟» في مركز القرارات. القراءة
  تُعدَّل وتُحذف، والخانة التي تُفرَّغ تُمحى بدل أن تبقى على خطئها.
- **الرصد اليدوي فوق حكم الأرقام**: من رصد له مدربُه «وصل لنتيجة» لا يُنشأ له قرار
  «بلا تقدّم» لأن الميزان لم يتحرك — فالميزان لا يرى محيطًا نزل ولا ألمًا زال.
- **بحثٌ باسمٍ واحد**: من جدّد خمس مرات كان يملأ نتيجة البحث بخمسة أسطر. كل اسم يظهر
  مرة واحدة باشتراكه الأخير ومعه عدد اشتراكاته، وزرٌّ يعيد العرض الكامل (كل تجديد
  بسطره) للمراجعة المحاسبية.
- **الصفحة تعود كما تركتها**: الشهر والفرع وبقية الفلاتر في عنوان الصفحة — التحديث أو
  زرّ الرجوع لا يُعيدانك للبداية، والرابط يُنسخ لزميل فيرى ما تراه. وبعد تنفيذ إجراء
  تبقى في مكانك من القائمة، ويبقى الجدول على صفحته وكلمة بحثه.
- **سهل الاستخدام على الموبايل والكمبيوتر** — واجهة متجاوبة بالكامل، والنافذة المنبثقة
  تتصرّف كنافذة: Escape يغلقها، والتركيز يقع على أول حقل ويدور داخلها ولا يخرج، ويعود
  لزرّ الفتح عند الإغلاق.
